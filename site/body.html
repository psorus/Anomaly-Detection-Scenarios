Scenario-specific benchmarking

Scenarios that group applications by what their algorithms must handle

A scenario groups applications that share structural properties: data modality, anomaly type, supervision, processing time, evaluation priority and operational constraints. Domains are contextual properties and never define a scenario. Each scenario here is an explicit rule over structural properties, and membership is computed from the catalog, so one application can sit in several scenarios.

Datasets per scenario

Datasets mapped to scenarios

Every dataset is linked to the applications it comes from and graded by readiness: benchmark suites and benchmark datasets have curated labels and protocols, application data was released with applied work and is closer to deployment, with gaps, irregular sampling and partial labels. A dataset counts for a scenario only if it is labeled, comes from a member application, fits the scenario's modality and carries the annotations the scenario's required outputs need, such as severity grades or root causes. Generic collections like ADBench are shown but not counted.

How the catalog was built

The first version was drafted with Claude (Anthropic) in October 2026, and every record starts as a draft until a contributor checks it against sources. Claude compiled the applications from the anomaly detection literature and practice across 20 domains and coded each one with the structural properties of its most common deployment. Real deployments vary; where one domain runs two very different setups (an inline payment scorer and a batch investigation queue), they appear as two applications.

The dataset catalog links each dataset to the applications it comes from. Recent datasets (2023 to 2026) were checked against their papers or project pages. Links marked found in search appeared in search results while the catalog was built; other dataset-page addresses come from Claude's knowledge and were not checked one by one. Every dataset also has a Google Scholar search link. Sizes are given only where they could be stated with confidence. Many applications still have no public dataset, which is itself a gap for scenario-specific benchmarking.

Where the paper itself cites a source for an application or dataset, its sheet shows the reference under In the paper.

Treat draft codes as a starting point for the taxonomy workshops the paper proposes. Each sheet shows whether a record is still a draft or has been reviewed, and links to the file, its history and its discussion on GitHub.

Scenario rules are explicit (open any scenario to see its rule). The builder tab derives scenarios bottom-up from the same codes, so curated and data-driven groupings can be compared.

Contribute

Every number here comes from a file anyone can change

Each application, dataset and scenario is one small text file in the GitHub repository. Change a file through a pull request and, once it is merged, this site rebuilds itself and every count, pie and scenario member list is recomputed from the files. Nothing on the site is typed in by hand.

Fix what you see

Open any scenario, application or dataset. Edit on GitHub opens its file in GitHub's editor; GitHub forks the repository for you and turns the edit into a pull request. A bot then posts which scenarios and counts your change affects.

Back every changed property with a source under evidence. Reviewers merge changes that are backed by evidence.

Propose something new, without YAML

Fill in a form. A maintainer checks it and a workflow turns it into a pull request with the file already written.

Write the file yourself

Start from a template with the next free id filled in.

The scenario builder can also turn any group it finds into a scenario file with the rule filled in.

Debate a scenario

Disagreements about requirements, rules or metrics belong in GitHub Discussions, one thread per record. Every sheet links to its thread. Decisions are recorded in the pull request that changes the file.

Why the numbers are defensible

Only primary facts are stored: how each application is coded, each scenario's rule, each dataset's properties and links, and the evidence for them. Everything else is derived by one script: an application belongs to a scenario if it matches the scenario's rule; a dataset qualifies for a scenario if one of its applications is a member and it has the modality and annotations the scenario needs; a dataset counts toward a scenario's minimum unless it is a generic collection or unlabeled.

Each change is a commit with an author, a reason and a review, so any number can be traced back to the edits that produced it. To cite a fixed state, cite a tagged release; its catalog.json reproduces every number on the site.
